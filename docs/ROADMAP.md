# Fathom 路线图

更新：2026-09-22。方向由用户 2026-09-13 明确：**将当前开发线收敛为 v0.3.0，先成为其他 Mac 用户可安装、可验证更新的桌面应用；源码先托管在私有仓库，后续开放；远期提供目录、依赖与扫描结果的智能解释。**

## 产品定位

Fathom 回答三个连续的问题：空间发生了什么变化 → 变化来自哪里 → 这些内容有什么用、处理它会影响什么。近期交付前两步，远期用本地规则与可选 Agent 增强第三步。

目标用户首先是频繁使用 AI 编程工具、包管理器和模型工具的 Mac 用户，同时保留普通用户的目录容量追踪路径。核心价值是可追溯的历史变化与用途解释，不把重复文件、全盘文件索引或自动删除作为首发条件。

成功的首次体验：在没有 Python/Rust/Homebrew 的测试账户中，安装并启动 → 看懂监控范围和权限 → 完成首扫 → 看见有效基线 → 到第二个有效日期能解释变化。成功的日常体验：从总览结论至具体目录证据，最多三次主要导航操作；关闭窗口后后台状态仍真实。

## 执行顺序与投入边界

当前收敛重点（2026-09-22）：把已实现的注册/设置/更新入口连成可验证的发行路径，尤其是更新前停写、备份和失败恢复；同步完成原生体验、新账户安装、依赖声明和双架构产物。实现缺口与人工环境缺口分别处理，不能把所有剩余工作归为人工门。具体领取、在途归属与顺序只见 TASKS；不为维持派发增加视觉微调、重复夹具或远期智能功能。

以下是阶段依赖和投入约束，已完成条目保留其理由，**不是当前任务队列**。

1. 先做 ISS-018，阻止坏数据替换好数据；随后处理路径、比较语义和本地接口边界。ISS-025 提供后续迁移与隔离基础，ISS-020 统一 CLI/API/定时扫描生命周期。
2. UX 原型 ISS-026 可提前做，避免修完技术问题后才讨论产品体验。先保留五页信息架构，升级结论、证据、详情与状态组织；不增加一个用途模糊的“AI 聊天”首页。
3. ISS-029 以新账户中的运行时/后台服务小样验证安装方案，再做 ISS-009。只产出一个打开现有本机服务的 `.app` 不满足分发目标。
4. ISS-031 固定可复现 CI 和两个 macOS 架构基础；ISS-040/041 必须等待自包含 app、后台退出协议和正式 UI。v0.3.0 先生成 private draft Release，真实下载与 N→N+1 通过后再进入公开门。
5. 功能扩展必须通过同一套数据、状态和验证入口。前端优先拆分原生模块；保留 FastAPI、SQLite、系统 du 与 Tauri，不因审查而整体重写技术栈。
6. M4 先做有限识别器（例如 Python 环境、Node 依赖与缓存），再接一个可替换 Agent 适配器。初期无需任意工具执行、多个 Agent 编排或后台自动外传。

## 主要风险与取舍

- 目录累计占用与整卷可用空间口径不同，APFS/共享块、权限和阈值可能造成差异；不承诺清理某目录一定释放同等字节。
- 包内 Python、后台服务、TCC 权限与升级的组合尚未验证。优先验证“自包含运行时 + 单一后台服务所有者”，备选与停止条件见 [目标方案](plans/2026-09-12-delivery-and-intelligence.md)。
- 陌生用户安装要求依赖固定、服务可诊断和发行许可清晰。Apache-2.0 已选定，私有托管与公开发布仍是不同步骤；公开时机由用户决定。
- 私有 GitHub Release 不能作为普通用户的匿名更新源。v0.3.0 外部自动更新前必须转公开，或使用独立公开下载仓/CDN；客户端不得内嵌 GitHub PAT。
- 智能解释的误判成本高于描述流畅度。评估重点是来源准确、未知保留、共享依赖不误导；不使用“多数回答看起来不错”作为上线证据。

页面体验合同见 [DESIGN](DESIGN.md)；实施任务及阻塞在内部任务跟踪维护。
